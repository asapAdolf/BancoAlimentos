================================================================================
1. VISIÓN GENERAL Y ARQUITECTURA DEL SISTEMA
================================================================================
Rescate Alimentario es una plataforma diseñada para reducir el desperdicio de
alimentos conectando establecimientos (restaurantes, panaderías, supermercados)
con beneficiarios (personas particulares y organizaciones de ayuda humanitaria).

La arquitectura general se compone de tres capas principales:

  [ FRONT-END: React 19 + TypeScript + Vite ]
         │ (Peticiones HTTP / JSON con REST API)
         ▼
  [ BACK-END: Express (TS) con Patrones de Diseño / Flask (Python) con ORM ]
         │ (Consultas SQL vía SQLAlchemy / psycopg2 / In-Memory Driver)
         ▼
  [ BASE DE DATOS: PostgreSQL (BancoAlimentos) ]

Características clave de diseño:
- Desacoplamiento: La interfaz de usuario no conoce la estructura interna de la
  base de datos ni los algoritmos de cálculo.
- Extensibilidad: Nuevos métodos de entrega, notificaciones o reglas de negocio
  se integran mediante patrones sin alterar el código existente (Principio Open/Closed).

3. FRONT-END: FUNCIONAMIENTO Y DISTRIBUCIÓN DE ARCHIVOS
================================================================================
El Front-End está desarrollado en React 19 con TypeScript, utilizando Vite como
entorno de compilación y servidor de desarrollo ultrarrápido.

3.1. Flujo de Inicialización
----------------------------
1. El navegador carga `index.html`.
2. `index.html` invoca `src/main.tsx`.
3. `main.tsx` monta el componente raíz `<App />` dentro del elemento `#root`.
4. `App.tsx` envuelve la aplicación en dos contextos globales:
   - `<AuthProvider>`: Mantiene la sesión del usuario actual (persona, donante, etc.).
   - `<PlataformaProvider>`: Gestiona el estado de publicaciones, reservaciones,
     notificaciones e impacto ambiental en memoria reactiva.
5. `App.tsx` define las rutas mediante React Router (`react-router-dom`):
   - `/`: PaginaInicio (Landing promocional)
   - `/catalogo`: PaginaCatalogo (Listado interactivo de alimentos)
   - `/alimento/:id`: PaginaDetalle (Detalle y reserva de alimento)
   - `/publicar`: PaginaPublicar (Formulario para establecimientos)
   - `/mis-publicaciones`: PaginaMisPublicaciones (Gestión del comercio)
   - `/reservaciones`: PaginaReservaciones (Historial de apartados)
   - `/notificaciones`: PaginaNotificaciones (Bandeja de avisos)
   - `/estadisticas`: PaginaEstadisticas (Impacto ecológico y CO2 evitado)
   - `/ubicacion`: PaginaUbicacion (Mapa interactivo de donantes)
   - `/login` y `/registro`: Autenticación del sistema

3.2. Distribución de Responsabilidades en el Front
--------------------------------------------------
- `src/components/layout/`:
  - `Navbar.tsx`: Barra superior con cambio de usuario demo y accesos rápidos.
  - `PanelLayout.tsx`: Contenedor principal con barra lateral para usuarios autenticados.
  - `Footer.tsx`: Pie de página informativo.

- `src/components/catalog/`:
  - `TarjetaAlimento.tsx`: Renderiza la card de cada producto con su insignia
    (Donación, Descuento, Venta), precio calculado y botón de apartado.
  - `FiltrosCatalogo.tsx`: Barra lateral de filtrado por categoría, precio máximo,
    zona geográfica y ordenamiento.

- `src/components/ui/`:
  - Componentes modulares y reutilizables: modales (`Modal.tsx`), gráficas SVG
    (`GraficaBarras.tsx`, `GraficaDonut.tsx`), toasts de notificación (`Toasts.tsx`),
    estados vacíos (`EstadoVacio.tsx`) y visualizador simulado de mapas (`MapaDemo.tsx`).

- `src/context/`:
  - `AuthContext.tsx`: Almacena el usuario activo (`usuarioActual`), sus permisos
    y permite alternar entre perfiles demo rápidamente.
  - `PlataformaContext.tsx`: Actúa como cliente de datos. Contiene los métodos
    `publicarAlimento()`, `reservarAlimento()`, `confirmarEntrega()` y dispara
    las alertas visuales correspondientes.


================================================================================
4. BACK-END: ARQUITECTURA, FLUJO DE EJECUCIÓN Y CAPAS
================================================================================
El Back-End sigue una arquitectura en capas desacoplada. Cuando llega una
petición HTTP (por ejemplo `POST /api/publicaciones`):

  1. CAPA DE RUTAS (`src/rutas/`):
     Recibe la petición HTTP, extrae parámetros y encabezados (ej. `x-usuario-id`).
  2. CAPA DE VALIDACIONES (`src/validaciones/`):
     Comprueba que los datos obligatorios estén presentes y que los rangos de
     precios, fechas y porcentajes sean coherentes. Si fallan, lanza excepciones
     de tipo `IllegalArgumentException`.
  3. CAPA DE SERVICIOS (`src/servicios/`):
     Contiene las reglas de negocio. Por ejemplo, `PublicacionServicio` coordina
     con `PublicacionFactory` para construir la entidad adecuada, la persiste y
     luego usa `CatalogoAlimentos` para notificar a los suscriptores.
  4. CAPA DE PATRONES (`src/patrones/`):
     Ejecuta las abstracciones puras del dominio (fábricas, adaptadores,
     estrategias y observadores).
  5. CAPA DE DATOS / PERSISTENCIA (`src/datos/` y `Database/`):
     Guarda y recupera los objetos en memoria o en PostgreSQL.


================================================================================
5. PATRONES DE DISEÑO EN EL BACK-END (ANÁLISIS PROFUNDO)
================================================================================

--------------------------------------------------------------------------------
5.1. FACTORY METHOD (Creación de Publicaciones de Alimentos)
--------------------------------------------------------------------------------
¿Qué problema resuelve?
El sistema maneja tres tipos de publicaciones con reglas y cálculos completamente
distintos:
  - Venta directa: Se vende al precio base original.
  - Descuento: Se calcula un precio rebajado según una estrategia o porcentaje.
  - Donación: El precio final siempre es exactamente 0.00.

Si usáramos `if-else` o `switch` por todo el código para verificar el tipo,
cualquier cambio rompería el sistema.

Archivos involucrados:
- `backend/src/patrones/factory/PublicacionAlimento.ts` -> Interfaz Producto común.
  Declara métodos obligatorios:
  - `getModalidad(): Modalidad`
  - `calcularPrecioFinal(): number`
  - `getPorcentajeDescuento(): number`
  - `mostrarPublicacion(): void`
  - `toJSON(): PublicacionDTO`

- Clases Concretas (Productos):
  - `PublicacionVenta.ts`: `calcularPrecioFinal()` devuelve `precioBase`.
  - `PublicacionDonacion.ts`: `calcularPrecioFinal()` devuelve estrictamente `0`.
  - `PublicacionDescuento.ts`: Aplica el patrón Strategy para deducir el porcentaje
    y calcula `precioBase * (1 - descuento / 100)`.

- `backend/src/patrones/factory/PublicacionFactory.ts` -> La Fábrica (Creator):
  Contiene el método estático:
  `PublicacionFactory.crearPublicacion(tipo: string, datos: DatosPublicacion)`
  Evalúa el string `tipo` y retorna la instancia concreta correspondiente sin
  que el cliente conozca los detalles de instanciación.

--------------------------------------------------------------------------------
5.2. ADAPTER (Notificaciones y Proveedores de Mapas)
--------------------------------------------------------------------------------
¿Qué problema resuelve?
El sistema necesita comunicarse con servicios externos que tienen interfaces,
métodos y parámetros incompatibles entre sí:
1. En notificaciones: SMS, WhatsApp y Correo Electrónico.
2. En mapas: Google Maps y OpenStreetMap.

Archivos involucrados en Notificaciones:
- `backend/src/patrones/adapter/notificaciones/Notificacion.ts` -> Interfaz Target:
  ```typescript
  export interface Notificacion {
    enviarMensaje(mensaje: string): void;
  }
  ```
- Clases Adaptadas (Adaptees / Servicios externos simulados):
  - `SMS.ts`: Tiene su propio método `enviarMensaje(mensaje)` con límites de SMS.
  - `Whatsapp.ts`: Requiere un formato de mensaje para chat móvil.
  - `Email.ts`: Maneja concepto de asunto y remitente.
- Adaptadores (Adapters):
  - `smsAdapter.ts` implementa `Notificacion` envolviendo una instancia de `SMS`.
  - `whatsappAdapter.ts` implementa `Notificacion` envolviendo `Whatsapp`.
  - `emailAdapter.ts` implementa `Notificacion` envolviendo `Email`.

Archivos involucrados en Mapas:
- `backend/src/patrones/adapter/mapas/Mapa.ts` -> Interfaz común con:
  - `obtenerCoordenadas(direccion: string): Coordenadas`
  - `calcularRuta(origen, destino): Ruta`
- Clases Adaptadas: `GoogleMaps.ts` y `OpenStreetMap.ts`.
- Adaptadores: `googleMapsAdapter.ts` y `openStreetMapAdapter.ts`.

El resto del sistema solo invoca `mapa.calcularRuta(...)` o `notificador.enviarMensaje(...)`,
siendo indiferente a cuál proveedor físico está activo.

--------------------------------------------------------------------------------
5.3. STRATEGY (Cálculo Dinámico de Descuentos)
--------------------------------------------------------------------------------
¿Qué problema resuelve?
Un alimento en descuento no siempre se descuenta de la misma manera:
- Puede descontarse por **proximidad a caducidad** (a menos días restantes, mayor descuento).
- Puede descontarse por **disponibilidad o sobreinventario** (a mayor volumen estancado, mayor descuento).

Archivos involucrados:
- `backend/src/patrones/strategy/DescuentoStrategy.ts` -> Interfaz de la Estrategia:
  ```typescript
  export interface DescuentoStrategy {
    calcularDescuento(alimento: Alimento, porcentajeMaximo: number): number;
    getTipo(): EstrategiaDescuento;
    getDescripcion(): string;
  }
  ```
- Estrategias Concretas:
  - `DescuentoPorCaducidad.ts`: Calcula los días entre hoy y la fecha de caducidad.
    Si vence hoy: aplica el 100% del porcentaje máximo fijado.
    Si vence en 1 día: aplica el 80%, etc.
  - `DescuentoPorDisponibilidad.ts`: Revisa la cantidad de unidades en almacén.
    Si hay más de 20 unidades: aplica el 100% del porcentaje permitido.
  - `crearEstrategia.ts`: Fábrica auxiliar para instanciar la estrategia según el texto
    ('caducidad' o 'disponibilidad').

--------------------------------------------------------------------------------
5.4. OBSERVER (Catálogo y Suscripciones en Tiempo Real)
--------------------------------------------------------------------------------
¿Qué problema resuelve?
Cuando un establecimiento publica un alimento nuevo, múltiples usuarios
interesados deben ser notificados sin que el catálogo deba acoplarse a cada uno.

Archivos involucrados:
- `backend/src/patrones/observer/Observador.ts` -> Interfaz del Observador:
  ```typescript
  export interface Observador {
    actualizar(mensaje: string, publicacion: PublicacionAlimento): void;
    getId(): string;
  }
  ```
- `backend/src/patrones/observer/CatalogoAlimentos.ts` -> Sujeto (Subject):
  Mantiene una lista privada de observadores `private observadores: Observador[] = []`.
  Métodos:
  - `agregarObservador(obs: Observador)`
  - `eliminarObservador(obs: Observador)`
  - `notificar(mensaje, publicacion)`: Recorre la lista y llama a `obs.actualizar(...)`.
  - `nuevoAlimento(publicacion)`: Dispara la notificación colectiva al publicar.
- `backend/src/patrones/observer/UsuarioObservador.ts` -> Observador Concreto:
  Representa a un usuario suscrito. Al recibir `actualizar(...)`, utiliza su
  adaptador de notificación configurado (SMS, WhatsApp o Email) para transmitir
  el mensaje a su dispositivo.

6.1. CÓMO AGREGAR UNA NUEVA MODALIDAD A FACTORY METHOD (Ej. "Subasta")
--------------------------------------------------------------------------------
Imagina que deseas permitir donaciones especiales o publicaciones por "Subasta".

Paso 1: Crear la clase concreta del producto
Crea el archivo `backend/src/patrones/factory/PublicacionSubasta.ts`:
```typescript
import { PublicacionAlimento, DatosPublicacion, PublicacionDTO } from './PublicacionAlimento.js';
import { Modalidad } from '../../modelos/tipos.js';

export class PublicacionSubasta implements PublicacionAlimento {
  id: string;
  alimento: any;
  horarioRecoleccion: any;
  establecimiento: any;
  estadoActual: any;
  precioBase: number;
  fechaPublicacion: string;

  constructor(datos: DatosPublicacion) {
    this.id = datos.id;
    this.alimento = datos.alimento;
    this.horarioRecoleccion = datos.horarioRecoleccion;
    this.establecimiento = datos.establecimiento;
    this.estadoActual = datos.estadoActual ?? 'disponible';
    this.precioBase = datos.precioBase;
    this.fechaPublicacion = datos.fechaPublicacion ?? new Date().toISOString();
  }

  getModalidad(): Modalidad {
    return 'subasta' as Modalidad; // Asegúrate de agregar 'subasta' al type Modalidad
  }

  getPorcentajeDescuento(): number {
    return 0;
  }

  calcularPrecioFinal(): number {
    // La subasta arranca en el 50% del precio base como postura inicial
    return this.precioBase * 0.50;
  }

  mostrarPublicacion(): void {
    console.log(`[SUBASTA] ${this.alimento.nombre} - Puja inicial: $${this.calcularPrecioFinal()}`);
  }

  toJSON(): PublicacionDTO {
    return {
      id: this.id,
      modalidad: this.getModalidad(),
      alimento: this.alimento,
      horarioRecoleccion: this.horarioRecoleccion,
      establecimiento: this.establecimiento,
      estadoActual: this.estadoActual,
      precioBase: this.precioBase,
      porcentajeDescuento: 0,
      precioFinal: this.calcularPrecioFinal(),
      fechaPublicacion: this.fechaPublicacion
    };
  }
}
```

Paso 2: Registrar la clase en la fábrica
Abre `backend/src/patrones/factory/PublicacionFactory.ts` y añade el nuevo caso:
```typescript
import { PublicacionSubasta } from './PublicacionSubasta.js';

export class PublicacionFactory {
  static crearPublicacion(tipo: string, datos: DatosPublicacion): PublicacionAlimento {
    if (equalsIgnoreCase(tipo, 'venta')) {
      return new PublicacionVenta(datos);
    } else if (equalsIgnoreCase(tipo, 'descuento')) {
      return new PublicacionDescuento(datos);
    } else if (equalsIgnoreCase(tipo, 'donacion')) {
      return new PublicacionDonacion(datos);
    } else if (equalsIgnoreCase(tipo, 'subasta')) {
      return new PublicacionSubasta(datos); // <-- NUEVO ELEMENTO
    }
    throw new IllegalArgumentException('Tipo de publicación no válido');
  }
}
```
¡Listo! Todo el sistema consumirá la nueva modalidad sin tocar controladores ni vistas.

6.3. CÓMO AGREGAR UNA NUEVA ESTRATEGIA A STRATEGY (Ej. "Por Horario")
--------------------------------------------------------------------------------
Paso 1: Crear la clase que implementa `DescuentoStrategy`
Crea `backend/src/patrones/strategy/DescuentoPorHorario.ts`:
```typescript
import { DescuentoStrategy, porcentajeDe } from './DescuentoStrategy.js';
import { Alimento } from '../../modelos/Alimento.js';
import { EstrategiaDescuento } from '../../modelos/tipos.js';

export class DescuentoPorHorario implements DescuentoStrategy {
  calcularDescuento(alimento: Alimento, porcentajeMaximo: number): number {
    const horaActual = new Date().getHours();
    // Si ya pasa de las 20:00 hrs, liquidar con descuento total
    if (horaActual >= 20) {
      return porcentajeMaximo;
    } else if (horaActual >= 18) {
      return porcentajeDe(porcentajeMaximo, 0.70);
    }
    return porcentajeDe(porcentajeMaximo, 0.30);
  }

  getTipo(): EstrategiaDescuento {
    return 'horario' as EstrategiaDescuento;
  }

  getDescripcion(): string {
    return 'Descuento agresivo en horario nocturno previo al cierre';
  }
}
```

Paso 2: Registrar en `crearEstrategia.ts`:
```typescript
if (equalsIgnoreCase(tipo, 'horario')) {
  return new DescuentoPorHorario();
}
```

7. FLASK Y LA BASE DE DATOS POSTGRESQL
================================================================================
Para complementar o dar soporte a un backend en Python con persistencia relacional
robusta, se construyó una arquitectura en Flask integrada con PostgreSQL.

7.1. El Esquema Relacional (`Database/schema.sql`)
-------------------------------------------------
El archivo DDL contiene 25 tablas relacionales organizadas en dominios:
- Catálogos: `roles`, `zonas`, `unidades_medida`, `categorias_alimento`, `metodos_pago`.
- Seguridad y Personas: `usuarios`, `usuario_roles`, `tokens_sesion`.
- Establecimientos y Logística: `establecimientos`, `horarios_recoleccion`, `transportistas`.
- Alimentos y Operaciones: `alimentos`, `publicaciones`, `reservaciones`, `detalles_reservacion`.
- Trazabilidad e Impacto: `historial_publicaciones`, `notificaciones`, `calificaciones`.

7.2. Configuración y Variables de Entorno (`.env` y `app/config.py`)
--------------------------------------------------------------------
- Archivo `.env`:
  Guarda de forma segura las credenciales sin exponerlas en Git:
  `FLASK_APP=run.py`
  `DB_USER=postgres`
  `DB_PASSWORD=<tu_password>`
  `DB_HOST=localhost`
  `DB_PORT=5432`
  `DB_NAME=BancoAlimentos`
  `DATABASE_URL=postgresql://postgres:<tu_password>@localhost:5432/BancoAlimentos`

- Archivo `app/config.py`:
  Lee el archivo `.env` mediante `python-dotenv`, normaliza automáticamente prefijos
  `postgres://` a `postgresql://` (requerido por `SQLAlchemy 2.0` en proveedores nube
  como Render) y configura `pool_pre_ping=True` y `pool_recycle=300`.

7.3. Capa ORM y Modelos (`app/models.py` y `app/database.py`)
-------------------------------------------------------------
- `app/database.py`: Instancia `db = SQLAlchemy()`, evitando dependencias circulares.
- `app/models.py`: Mapea las tablas de PostgreSQL a clases de Python compatibles con
  Python 3.13 (`datetime.now(timezone.utc)`). Cada modelo ofrece `.to_dict()` para
  serialización JSON limpia.

7.4. Arquitectura Modular por Blueprints y API REST (`run.py` y `app/`)
-----------------------------------------------------------------------
`app/__init__.py` implementa el patrón Application Factory (`create_app()`) e integra:
- Vistas web segmentadas por rol mediante Blueprints:
  - `publico`: inicio, catálogo con filtros, detalle, mapa de ubicación y estadísticas.
  - `auth`: inicio de sesión y registro con contraseñas verificadas por hash (`Werkzeug`).
  - `panel`, `cliente`, `empresa`, `transportista` y `admin`: paneles operativos con
    control de acceso mediante decoradores en `app/seguridad.py` y menús en `app/utils.py`.
- Blueprint REST `api` (`/api/*` en `app/blueprints/api.py`):
  - `GET /api/salud`: ejecuta `SELECT 1` y reporta las 25 tablas detectadas en PostgreSQL.
  - `GET /api/roles`, `GET /api/categorias`, `GET /api/unidades`: catálogos esenciales.
  - `GET /api/usuarios` y `GET /api/publicaciones`: consulta de registros en PostgreSQL.
  - `POST /api/seed`: inserta los catálogos base si las tablas están vacías.

7.5. Scripts de Automatización (.bat) y Pruebas (`tests/`)
----------------------------------------------------------
- `arrancar.bat`: comprueba el servicio Windows de PostgreSQL e inicia el Front-End Vite.
- `arrancar_todo.bat`: verifica PostgreSQL y levanta el servidor Flask (`python run.py`)
  en `http://127.0.0.1:5000`.
- `tests/test_rutas.py`: suite de `pytest` que valida el estado inicial limpio, control de
  acceso por rol (`403`), registro/login y ciclo completo de publicación, reserva y entrega.

8. CAMBIOS DE PUESTA EN PRODUCCIÓN Y DESPLIEGUE EN RENDER
================================================================================

8.1. Resumen de Ajustes y Limpieza de Datos de Demostración
-----------------------------------------------------------
Para pasar el sistema de un prototipo demostrativo a un entorno operativo limpio:
1. Eliminación de registros no esenciales:
   - Se vaciaron todas las publicaciones, reservaciones, notificaciones, establecimientos
     ficticios y cuentas `@demo.mx` en `app/store.py`, `src/data/*` y `BaseDatosMemoria.ts`.
   - Las métricas de impacto inician en `0` y crecen únicamente con entregas reales.
   - Se conservaron únicamente los menús por rol, constantes de dominio, catálogos base
     en PostgreSQL (`roles`, `categorias_alimento`, `unidades_medida`) y la cuenta
     esencial de administración (`ADMIN_EMAIL` / `ADMIN_PASSWORD`), ya que el rol de
     administrador no es de registro público.
2. Seguridad y calidad de código:
   - En Flask (`app/store.py` y `app/blueprints/auth.py`), las contraseñas ahora se
     almacenan y validan con hash criptográfico (`generate_password_hash` / `check_password_hash`).
   - En las plantillas Jinja2 (`app/templates/`) se sustituyeron estilos en línea con
     interpolaciones por atributos `data-ancho`, `data-alto` y `data-color` procesados
     en `app/static/js/app.js`, eliminando errores del analizador CSS.
   - En React/TypeScript se ajustaron `tsconfig.app.json` y `tsconfig.node.json` con
     compilación incremental y se resolvieron las reglas de pureza/inmutabilidad del linter.

8.2. Cómo Funciona el Despliegue en Render
------------------------------------------
Render ejecuta la plataforma en la nube conectándose directamente a la rama `main` del
repositorio en GitHub (`asapAdolf/BancoAlimentos`) mediante dos recursos coordinados:

  [ GitHub (rama main) ]
            │ (Auto-Deploy en cada git push)
            ▼
  [ Render Web Service: Python + Gunicorn (`gunicorn run:app`) ]
            │ (Red privada interna vía `DATABASE_URL`)
            ▼
  [ Render PostgreSQL (`banco-alimentos-db` -> BD `BancoAlimentos`) ]

Componentes clave del despliegue:
1. Servidor WSGI de producción (`gunicorn`):
   En desarrollo local se usa `python run.py` (servidor interno de Flask), pero en
   producción Render ejecuta `gunicorn run:app` (incluido en `requirements.txt`), el
   cual importa el objeto `app = create_app()` de `run.py` y atiende peticiones
   concurrentes de forma estable.
2. Conexión a Base de Datos (`DATABASE_URL` en `app/config.py`):
   Render inyecta la cadena de conexión interna de PostgreSQL en la variable de entorno
   `DATABASE_URL`. `app/config.py` convierte automáticamente el esquema `postgres://` a
   `postgresql://` para cumplir con `SQLAlchemy 2.0` y activa `pool_pre_ping=True` para
   reconectar de forma transparente si una conexión inactiva se cierra.
3. Despliegue declarativo con `render.yaml` (Blueprint):
   El archivo `render.yaml` en la raíz define como código tanto la base de datos
   `banco-alimentos-db` como el servicio web `banco-alimentos`, configurando:
   - `buildCommand: pip install -r requirements.txt`
   - `startCommand: gunicorn run:app`
   - `healthCheckPath: /api/salud` (Render verifica continuamente que Flask y PostgreSQL
     respondan HTTP 200 antes de dirigir tráfico a la nueva versión).
   - Generación automática de secretos (`SECRET_KEY` y `ADMIN_PASSWORD`).
4. Inicialización de esquema y catálogos en la nube:
   Una vez creada la instancia PostgreSQL en Render:
   - Se ejecuta una única vez el DDL `Database/schema.sql` usando la *External Database URL*
     (`psql "<EXTERNAL_DATABASE_URL>" -f Database/schema.sql`) para crear las 25 tablas.
   - Se invoca `POST https://<tu-servicio>.onrender.com/api/seed` para poblar los
     catálogos operativos esenciales (`roles`, `categorias_alimento`, `unidades_medida`).
